## 3. Findings — VERIFIED

### F1 — No retry data exists anywhere in the execution model — VERIFIED
`backend/src/models/WorkflowExecution.ts:140-211` defines no `attempts`, `nextAttemptAt`,
`retryPolicy`, or `lastErrorCode` field. Statuses are limited to `queued`, `running`,
`completed`, `failed`, `compensating`, `compensated`, `compensation_failed`.

**This corrects the Week 3 plan's statement that "retry counts/timing may be recorded".** They
are not recorded in any form.

### F2 — `retry` is documented but no code reads it — VERIFIED
`docs/workflow-graph-contract.md:83` declares `retry?: { attempts: number; backoffMs: number };`.
A recursive search of `backend/src` for `retry`, `backoff`, and `attempt` returns only prose
strings and unrelated test names. There is no reader, no validator, and no execution path.

### F3 — `retry` leaks into the action handler input — VERIFIED (defect)
`backend/src/services/execution.runtime.ts:333-336` strips only `compensationAction` and
`compensationConfig` before dispatch. `retry` and `timeoutMs` remain in the object passed to
`action.execute(input)` at `execution.runtime.ts:906-910`, so a handler that forwards its input
transmits an execution-control field to the downstream service.

`execution.runtime.test.ts:206` asserts `receivedInput` equals the full task config, so
removing the field is a contract change → decision D1, not a unilateral edit.

### F4 — Terminal failure persistence is implemented and guarded — VERIFIED
`execution.service.ts:297-333` writes `status`, `nodeResults`, `error`, and `completedAt` under
the optimistic filter built by `buildExecutionUpdateFilter` (`execution.service.ts:30-45`).
If the write fails or matches no document, it throws `EXECUTION_RESULT_PERSISTENCE_FAILED`
(`execution.service.ts:313-331`) rather than reporting a terminal state it did not persist.
No fabricated success on the persistence path.

### F5 — Timeout stops waiting, not the handler — VERIFIED
`execution.runtime.ts:376-404`. A late handler settlement is discarded and the recorded
failure is retained. Consequently a retried timeout on a side-effecting task can duplicate the
side effect. Documented, not fixed.

### F6 — No queue, worker, or mid-execution state — VERIFIED
`startExecution` runs the graph synchronously inside the request
(`execution.service.ts:265`). `currentNodeId` is declared and returned by the API but written
`null` once at creation (`execution.service.ts:179`) and never updated, so it is always `null`
in the database. `nodeResults` persist only at compensation checkpoints and at terminal state.
There is no durable "attempt N of M" or "current step" source — relevant to both retry work and
WebSocket tracing.

### F7 — Saga compensation is unchanged — VERIFIED
Reverse completion order, per-node checkpoints, and separate compensation errors all still
behave as before; the 25 pre-existing service tests pass unmodified.

## 4. Tests added (4)

`backend/src/services/execution.runtime.test.ts`
1. `does not redispatch a failed task even when the node declares a retry policy` — asserts the
   handler is invoked exactly once and the node records exactly one failed result.
2. `records a single attempt when a task handler throws and retry metadata is present` — asserts
   a thrown handler maps to `ACTION_HANDLER_FAILED` with exactly one invocation.

`backend/src/services/execution.service.test.ts`
3. `does not retry a failed task when the node declares a retry policy` — asserts one `running`
   update then one terminal `failed` update, with `error` and `completedAt` persisted; no
   retry-wait state is produced.
4. `dispatches each task exactly once per execution when a later task fails` — duplicate-dispatch
   guard: each node is dispatched exactly once, and the node-result sequence is
   `trigger completed → task-a completed → task-b failed`.

Test-fixture change only: `SagaTask` gained an optional `retry` field and `sagaWorkflow`
passes it through. No production file was modified.
