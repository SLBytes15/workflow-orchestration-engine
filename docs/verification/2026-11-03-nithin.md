## 3. Concurrency implications

The current service can overlap multiple independent `executeWorkflowGraph()` calls when the Node.js process receives them concurrently, provided the actions are asynchronous. That is not the same as supporting 1,000 distributed pipelines end-to-end.

The main constraints are:

1. **Request-path execution:** each HTTP request remains occupied until graph execution and persistence finish. There is no durable job acceptance boundary.
2. **Sequential graph path:** nodes in one execution are awaited one after another. Independent branches are not scheduled in parallel by the runtime.
3. **Persistence pressure:** every execution performs several MongoDB writes, and the default connection-pool behaviour has not been measured or explicitly sized for the target.
4. **Single-process event dispatch:** Change Stream processing is intentionally serialized, so a slow matching workflow can delay later event handling.
5. **Single-process real-time state:** WebSocket tickets and subscriber maps are not shared between backend instances and are lost on restart.
6. **Timeout limitation:** the runtime timeout stops waiting but does not cancel the action. Slow external actions can continue consuming resources after the execution has already failed.
7. **Retry is not execution:** retry metadata is validated and removed from the downstream action payload, but the current runtime performs one attempt only. This is an explicit existing limitation, not a new change.

## 4. Repeatable local baseline harness

Added `backend/scripts/benchmark-execution-concurrency.ts`.

The harness:

- Builds a minimal valid `trigger -> task` graph.
- Uses a synthetic asynchronous delay as the task action.
- Starts multiple calls to the existing `executeWorkflowGraph()` concurrently.
- Counts completed and failed executions.
- Records the maximum number of simultaneously active synthetic actions.
- Reports average elapsed time and throughput across repetitions.
- Does not use HTTP, MongoDB, tenant records, WebSockets, Change Streams, or external actions.

Usage:

```powershell
cd backend
npx tsx scripts/benchmark-execution-concurrency.ts
npx tsx scripts/benchmark-execution-concurrency.ts --concurrency=1,5,10,25 --duration=25 --repetitions=2
```

This harness measures runtime overlap only. It must not be described as an API load test, database benchmark, ECS benchmark, or proof of 1,000 concurrent distributed executions.

## 7. Bottleneck and recommendation priority

### Mandatory before claiming the official target

1. Define whether the target means active runtime executions, accepted HTTP requests, or completed persisted executions.
2. Build an isolated HTTP-plus-database harness with unique test tenants/workflows and cleanup.
3. Establish MongoDB pool sizing, indexes, and monitoring for the staging environment.
4. Measure request-path execution under gradual load and record active executions separately from request count.
5. Decide how execution admission, retries, and long-running work should behave when the request path is saturated.

### High-risk architecture work requiring approval

- Durable queue and worker execution model.
- Shared coordination or pub/sub for multi-instance WebSocket updates.
- Durable or shared WebSocket ticket storage.
- Cancellation semantics for timed-out external actions.
- Parallel branch scheduling and per-tenant concurrency limits.

These changes are intentionally not implemented in this task because the task explicitly prohibits introducing a new queue, Redis, worker framework, or major architecture change without approval.

### Safe follow-up

- Add an approval-backed HTTP/staging harness that tracks request-to-completion lifecycle.
- Add explicit database pool configuration only after staging measurements and team agreement.
- Add observability for active executions, action duration, persistence latency, event-loop delay, and Change Stream queue depth.
- Revisit the single promise-chain Change Stream dispatcher if event throughput becomes a measured bottleneck.
