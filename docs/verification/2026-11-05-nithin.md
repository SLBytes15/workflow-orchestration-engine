## 3. Execution path today (task A)

1. **Start route and service.** `POST /api/workflows/:workflowId/executions`, `requireTenantAuth`, tenant derived from the API key, never from the body. Calls `executionService.startExecution`. VERIFIED.
2. **In-request execution, no worker.** `startExecution` creates the record `queued`, conditionally flips it to `running`, then `await`s `executeWorkflowGraph(...)` inline and writes the terminal state. No queue, no job broker, no resumption point. `member/nithin` and `origin/main` both contain exactly one `await executeWorkflowGraph(`; there is no `setImmediate`/`setTimeout` detach. VERIFIED.
3. **Scheduling and coordination.** Active executions are not scheduled by anything: one HTTP request equals one execution. Event-triggered executions are dispatched from the change-stream watcher through a single serialised promise chain, so a slow execution delays every later event in that process. VERIFIED.
4. **Multi-instance safety.** `changeStreamWatcher.service.ts` is byte-identical between `member/nithin` and `origin/main` (absent from `git diff --stat HEAD origin/main -- backend/src`). Every instance calls `BusinessEventModel.watch` and dispatches on every matching insert with no claim, lease or dedupe, and no resume token. Horizontal scaling therefore multiplies event-triggered executions. VERIFIED (risk).
5. **State persistence.** Statuses `queued | running | completed | failed | compensating | compensated | compensation_failed`. A successful run writes terminal state once; mid-run writes happen only at compensation checkpoints; node-level `startedAt`/`completedAt` are now recorded per node result. `currentNodeId` is still written `null` and never updated. A live run and a dead run remain indistinguishable from the execution document alone. VERIFIED.
6. **Timeout, failure, compensation.** Enforced per-node wait timeout (`ACTION_TIMEOUT`); a timed-out handler is not cancelled and its late settlement is discarded; compensation runs in reverse completion order via `invokeCompensation`; compensation errors are stored apart from the task error. Unchanged limitation: a timed-out node is recorded `failed`, so a late side effect escapes compensation. VERIFIED.
7. **Change stream / WebSocket blocking.** WebSocket publication is synchronous, guarded by `socket.readyState`, and every call site wraps it in `try/catch` (`publishPersistedExecution`, `safeNotify` in `execution.service.ts`). Publishing cannot fail or block an execution, and events are only sent after persistence returns. VERIFIED. Change-stream dispatch *does* block execution throughput (§3), but it is not the WebSocket layer.
8. **Database and shared state.** `mongoose.connect` sets only `serverSelectionTimeoutMS: 5000` — no pool sizing, no read/write concern, no replica-set assertion. One cluster shared by all tenants, isolated by `tenantId` filters. No advisory locks or distributed counters. The rate limiter is `express-rate-limit` with `windowMs: 15 * 60 * 1000`, `limit: 100`, default in-memory store, so the effective limit multiplies with instance count. VERIFIED.
9. **Duplicate requests and duplicate side effects.**
   - With a valid `Idempotency-Key`: duplicate POSTs do not create a second execution; the reservation is taken before dispatch, ownership is re-validated after the await, and the completed response is cached. A duplicate side effect is prevented **only if the downstream action honours the `idempotencyKey` passed to handlers** (`exec_<executionId>_<nodeId>`). Whether each action implementation forwards it is NOT VERIFIED.
   - Without the header: two identical POSTs create two executions and dispatch the graph twice. No dedupe exists at that level. VERIFIED.
   - The `IdempotencyRecoveryWorker` class exists but is instantiated **only in tests**; `startServer` never starts it, and `reconcileInFlightReservation` is not called from the request path. Consequence: after a process crash mid-execution, a retry with the same key receives 409 `IDEMPOTENCY_KEY_IN_FLIGHT` until the record's 24 h TTL expires. PARTIAL.

### Minimum viable plan (unchanged, Option A)

1. Classify by error code, default deny: retryable `HTTP_503`, `HTTP_429`, mapped connection/DNS failures; `ACTION_TIMEOUT` retryable only for actions declared non-side-effecting; everything else terminal.
2. Bounded attempts: 3 total dispatches, `backoffMs * 2^(n-1)` capped at 30 000 ms, jitter derived deterministically from `executionId + nodeId + attempt`.
3. Persist `attempts` and `lastErrorCode` **before** dispatch.
4. Exhaustion → `status: "failed"`, `attempts`, `lastErrorCode`, `deadLetteredAt`. No new `retrying` status; a waiting execution is `queued` with `nextAttemptAt`.
5. The DLQ is a tenant-scoped query over `deadLetteredAt`, not an in-memory list and not a new queue technology.

Requires schema decision D2 (additive nullable fields: `attempts`, `nextAttemptAt`, `lastErrorCode`, `deadLetteredAt`, `workerId`, `leaseExpiresAt`) and D6 (exhaustion semantics). Neither is approved.

## 5. Concurrency verdict against the 1,000+ requirement

| # | Limitation | Impact |
|---|---|---|
| 1 | Execution is synchronous inside the HTTP request | HTTP throughput and execution throughput are the same number; a long graph occupies a request slot for its whole duration |
| 2 | No lease / ownership / heartbeat | A crashed run is indistinguishable from a live one; recovery requires the unwired analysis in `executionRecovery.ts` |
| 3 | Unclaimed change-stream fan-out | Horizontal scaling duplicates event-triggered executions — the single biggest blocker for 1 000+ |
| 4 | No resume token | Events arriving during a restart window are lost |
| 5 | Per-process in-memory rate limiter (100 / 15 min) | Caps HTTP-level load long before the runtime is the limit; limit multiplies with instances |
| 6 | No pool sizing, single shared cluster | 1 000 concurrent writes will contend on the default pool; unknown headroom |

**Verdict:** the runtime overlaps concurrent work correctly (§1 L0), and request-level duplicate protection now exists when clients send `Idempotency-Key`. The architecture still cannot be described as supporting 1 000+ concurrent **distributed** executions: it is single-process, synchronous, unleased, and its event dispatch is not safe to scale horizontally.

## 6. Safe concurrency test plan (task C)

Counting definition must always be stated: **harness** = active from first node dispatch to last node settle (`maxActive`); **database** = records in `running` or `compensating`, which under-counts because terminal state is the only write for a successful run.

| Stage | Setup | Load | Stop conditions |
|---|---|---|---|
| L0 | In-process harness (available today) | 1 / 5 / 10 / 25 | any failure; `maxActive` < requested |
| L1 | Single instance + **isolated local** MongoDB replica set | 25 → 100 | any 429; pool wait > 100 ms; p95 > 5 s |
| L2 | Isolated staging database | 100 → 500 | RSS growth > 50 %; failure rate > 0.1 %; change-stream lag rising |
| L3 | Multi-instance behind a load balancer | 500 → 1 000 | any duplicate execution (fan-out bug); any unhealthy instance |
| L4 | Soak at 70 % of L3 peak, 30 min | — | memory without plateau; latency drift |

Metrics per stage: active executions (both definitions), throughput/s, p50/p95/p99 latency, failures by code, CPU/RSS, Mongo pool usage and op counters, change-stream lag, WebSocket subscriber count.

Rules: HTTP user load is measured separately from actual execution concurrency; no stage above L0 runs against the shared or live MongoDB; L1+ needs explicit approval for an isolated environment.

## 7. Minimal fix recommendation (task D)

### Recommended: start the existing idempotency recovery worker — **per tenant**

Verified constraint, found while preparing the patch: `IdempotencyRecoveryWorker` requires a `tenantId` in its constructor, and `mongoIdempotencyDependencies.findInFlightRecords` queries `{ tenantId, status: "in_flight" }`. There is no global mode, so a single process-wide worker cannot exist. Any wiring has to enumerate tenants. This corrects the first draft of this section and raises the estimate.

| Item | Detail |
|---|---|
| Files | `backend/src/index.ts` plus a small `backend/src/services/idempotencyRecoveryRunner.ts`; `executionIdempotency.ts` unchanged |
| Behaviour | On boot read `TenantModel.find({ status: "active" }).select("_id")`, construct one `IdempotencyRecoveryWorker(tenantId, mongoIdempotencyDependencies, { intervalMs: 60_000 })` per tenant, `.start()` each after `connectDatabase`; on shutdown `.stop()` all of them before closing HTTP. Tenants created after boot are not swept until the next restart — that limitation must be stated, not hidden |
| Why it matters | Without it, a crashed execution leaves an `in_flight` reservation that answers 409 to every retry for the record's full 24 h TTL. That is a correctness bug at any concurrency and it blocks safe retry testing |
| Acceptance criteria | 1) exactly one worker per active tenant, inactive tenants skipped; 2) every worker stopped on shutdown and none throw when never started; 3) a stale `in_flight` record older than the grace period reconciles to `RETRY_SAFE` or `COMPLETED_RECONCILED`; 4) a live reservation is untouched; 5) a tenant-enumeration failure logs and continues instead of killing startup; 6) existing `index.test.ts` startup/shutdown tests stay green |
| Tests | `index.test.ts` with an injected fake runner asserting worker count per tenant and start/stop calls; reuse the existing `IdempotencyRecoveryWorker` tests for reconciliation semantics; one test proving a second boot does not double-start |
| Risks | One query per tenant per minute and memory proportional to tenant count — acceptable at current scale, worth revisiting at 1 000+ tenants. A single global sweep is the better long-term design but needs a change to the shared idempotency dependency contract, so it is explicitly **not** proposed for this deadline |
| Estimate | 4–5 h including tests and review (revised up from 2–3 h; the first draft missed the per-tenant scope) |

### Not recommended before 10 November

Worker/queue infrastructure, distributed leases, a separate dead-letter collection, retrying side-effecting actions, compensation replay, change-stream single-consumer election, and any horizontal-scaling change. These need architecture approval and cannot be validated in the remaining days.

### Docs-only, no approval needed

State the non-retryable contract explicitly in `docs/backend/execution-contract.md` (“a declared `retry` policy is validated and stripped, never executed; every action failure is terminal”). Not applied in this commit.
