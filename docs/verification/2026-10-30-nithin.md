## 3. Implemented and tested today

### 3.1 Build unblock — `workflow.service.test.ts`

The two comparisons now narrow through `record.status as string`, so the
assertion keeps its original meaning while `tsc` accepts it. No behaviour change.

### 3.2 `POST /api/executions/ws-ticket` — ticket issuance

`backend/src/routes/executionWsTicket.routes.ts` mounts behind the existing
`tenantAuthMiddleware`. The tenant comes only from the resolved API key; a
`tenantId` in the request body is ignored. Response is `{ ticket, expiresAt }`
and nothing else.

### 3.3 Ticket lifecycle — `backend/src/services/executionTicket.service.ts`

32 random bytes (`node:crypto.randomBytes`) → base64url, 60 s TTL, single use,
removed from the map **before** the expiry check so a late redemption cannot be
retried. In-memory and single-process, which is the approved MVP limitation.

### 3.4 `/ws/executions` hub — `backend/src/services/executionWebSocket.ts`

`ws` attached to the existing HTTP server (no second listener). Handshake
requires a ticket; failure closes with `4401` and registers nothing. Sockets are
bucketed by the ticket's tenant, so a publish reaches only that tenant's sockets.
Client messages are ignored, `maxPayload` is 1 KiB, send/close/error never throw
into the caller. `compensated` and `compensation_failed` deliberately map to no
event type instead of being invented as `completed` / `failed`.

### 3.5 Publish-after-persistence — `execution.service.ts`

`startExecution` already wrapped the notifier in `safeNotify`; it now notifies
only with the document returned by a successful write, after the write. Tests pin
the ordering and the negative case.

### 3.6 Server lifecycle — `index.ts`

`attachWebSocket(server)` is called after `listen` and before the watcher
starts; shutdown closes the WebSocket server and its sockets **before** closing
the HTTP listener, and again on the startup-failure cleanup path.

## 5. Retry and failure persistence (Task 4 core) — unchanged by the WebSocket work

> D1 and D3 were approved later the same day; see §10 for the implemented change.

Nothing in the retry conclusions changed today:

- Terminal failure persistence is written under the optimistic filter and throws
  `EXECUTION_RESULT_PERSISTENCE_FAILED` rather than reporting an unpersisted
  terminal state (`execution.service.ts`).
- `retry: { attempts, backoffMs }` remains **inert**: no reader, no validator, no
  scheduler, and no retry state in `WorkflowExecution`. Existing tests still
  assert exactly one dispatch per node.
- Timeout is still wait-only; a late handler settlement is discarded, so retrying
  a side-effecting task can duplicate the effect.
- No queue, worker, durable DLQ, schema field, or idempotency key was added.

Design and open decisions: `docs/backend/week3-retry-failure-persistence.md`
(D1–D6). The new WebSocket work does not change them, but it does make one gap
more visible: `currentNodeId` is still never updated, so no per-step progress can
be streamed — only lifecycle transitions exist to publish.

## 6. Risks and limitations to state in the PR

1. **Tickets are process-local.** A restart invalidates every ticket, and two
   backend instances cannot honour each other's tickets. Approved for MVP;
   must not be presented as production-grade.
2. **The ticket travels in the query string** (frontend already merged that
   way). It is single-use and 60 s, so it is not a long-lived credential, but
   proxies that log full URLs will see it.
3. **No delivery guarantee.** A socket that is down misses the event; REST
   remains the source of truth and the frontend refetches on reconnect.
4. **`compensated` / `compensation_failed` emit nothing** until a mapping is
   approved. A client that only listens to sockets will not learn about those
   terminal states.
5. **`docs/websocket-execution-updates.md` is now stale for this branch.** It is
   scoped to `member/mahak` and still says the backend is pending; I did not
   edit another owner's document. Whoever owns it should update section L after
   this lands.
6. `workflow.service.test.ts` change is a **type-level fix only** and is included
   because the branch does not build without it.

## 10. Addendum — D1 and D3 approved and implemented

**Approved by Saransh, 30 October 2026:** D1 = strip + validate · D3 = synchronous
execution (no worker, no queue, no in-request retry sleeps).

### 10.1 What changed

`backend/src/services/execution.runtime.ts`, `parseTaskActionConfig`:

- **Validation.** When `retry` is present it must be a record with an integer `attempts` ≥ 1
  and a finite `backoffMs` ≥ 0; otherwise the node fails with `INVALID_RETRY_CONFIG`
  before any handler runs. `timeoutMs` keeps its existing positive/finite validation.
  The attempt cap from §5.2 of the design is **not** enforced here — an out-of-policy
  `attempts: 5` is still shape-valid, because range policy belongs to the future
  implementation, not to an inert field.
- **Stripping.** `retry` and `timeoutMs` are deleted from the task config before it reaches
  `action.execute(input)` and before it is copied into the compensation context's
  `taskConfig`. `timeoutMs` is still applied because the runtime reads it from the parsed
  config, not from the handler payload.
- **Nothing else.** Retry is still never acted on: one dispatch per node, no sleeps, no
  worker, no schema change, no queue, no new dependency.

The public visible change is intentional and approved: a handler can no longer observe
`retry`/`timeoutMs` in its input.
